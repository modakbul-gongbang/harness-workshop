요청: $ARGUMENTS

1. 루트 CLAUDE.md, 기본 계약, 관련 가이드와 현재 코드·테스트를 읽는다.
   인터뷰 경로가 있거나 `.artifacts/<slug>/interview.md`가 있으면 먼저 읽는다.
   제품 정책의 출처는 사용자 답변·확정 계약이며 구현 코드와 에이전트 제안은 그 대체물이 아니다.
2. `references/prd-template.md`로 `docs/tasks/<slug>/prd.md`를 작성한다.
   인터뷰의 중요한 결정·비범위·미해결 항목을 누락하지 않고 PRD 본문에 옮긴다.
   Git 제외 인터뷰 파일을 읽지 못해도 PRD만으로 요구사항과 근거를 이해할 수 있어야 한다.
3. AC마다 상황/입력 → 행동 → 관찰 가능한 기대 결과와 보존 동작을 쓴다.
   정상뿐 아니라 중요한 권한·빈 상태·경계·거절·복구 조건을 고른다.
   실제 값은 계약에서 정하며 현재 구현의 출력을 정답으로 복사하지 않는다.
   테스트 개수나 모든 층의 테스트를 의무화하지 않는다.
   구체적인 테스트 재사용·추가·명령·선택 이유는 implement-prd의 계획에 남긴다.
4. 검증 범위 표에 tests/api/ui 세 행과 적용 이유를 적는다.
   tests는 공통 검증으로 required다.
   API·UI는 변경과 위험에 따라 required 또는 not-applicable로 정한다.
   not-applicable은 관련 동작에 영향이 없다는 근거이며 도구 부재나 비용 때문에 선택하지 않는다.
   API·UI 영향이 불명확하면 required로 두고 조사한다.
5. 기대 결과의 정답과 빠진 실패·예외 조건을 사용자와 확인한다.
   사용자가 초안만 요청했다면 결정이 충분해도 초안으로 반환하고 확정·구현으로 넘어가지 않는다.
   제품 판단이 남으면 한 번에 한 질문씩 묻고 `확정 여부: **초안**`을 유지한다.
   질문이 넓으면 deep-interview로 돌아간다.
   미해결 항목이 없고 사용자 답변·기존 확정 계약이 근거를 제공할 때만 `확정 여부: **확정**`으로 바꾼다.
   이미 확정된 답을 다시 승인받지 않고, 에이전트 제안을 사용자 승인으로 기록하지 않는다.
6. 구현하지 않고 task도 활성화하지 않는다.
   구현까지 요청받았다면 확정 PRD 경로와 전달받은 게시 범위를 implement-prd에 넘겨 이어서 실행한다.
   PRD만 요청받았다면 해당 파일과 미해결 사항을 반환한다.
