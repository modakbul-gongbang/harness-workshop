# G-TESTING: 검증

## 정답과 필요한 테스트

- 기본 정답은 `docs/baseline-contract.md`, 변경의 정답은 사용자 답변에 근거한 확정 PRD AC-ID에서 가져온다.
  코드와 현재 출력을 정답으로 복사하지 않는다.
  불명확한 제품 정책은 질문하고 PRD에 반영한 뒤 테스트한다.
- 사람이 PRD를 확정할 때 기대 결과와 빠진 실패·예외 조건을 검토할 수 있게 구체적인 입력과 결과를 제시한다.
- 테스트는 중요한 정책·경계값·권한·상태 전환·회귀 방지를 최소한으로 보호한다.
  기존 테스트로 충분하면 재사용하고 테스트 개수·coverage 숫자를 완료 조건으로 삼지 않는다.
- 계획에 각 추가 테스트가 잡을 현실적인 버그, 기존 테스트로 부족한 이유, 검증 경계의 선택 이유를 기록한다.
  동일 동작의 중복이나 구조가 바뀔 때만 깨지는 테스트를 추가하지 않는다.
  변경 범위의 중복·구현 종속 테스트는 같은 보호를 유지하며 통합하거나 제거하고 이유를 남긴다.
- Unit은 중요한 순수 정책·경계값, Integration은 실제 API·DB·파일 등의 연결, E2E는 소수의 핵심 사용자 흐름을 맡는다.
  매 AC마다 세 층을 모두 만들지 않는다.
  회귀 테스트는 별도 층이 아니며 버그를 재현하는 가장 낮고 안정적인 경계에 둔다.
- 소유 모듈(repository/service/controller/hooks)은 mock하지 않는다.
  허용 경계는 외부 서비스·시계·난수·브라우저 플랫폼이며 필요한 경우만 테스트 대역을 사용한다.
  함수 호출 횟수·private helper·CSS 클래스 대신 반환값·저장 결과·응답·사용자가 관찰하는 결과를 단언한다.
  기존 입력 계약의 경계 0/1/120/121자를 유지한다.

## 버그 수정과 실패 증거

- 버그 수정 전 재현 입력과 독립적인 기대값으로 회귀 테스트를 작성하거나 기존 테스트를 사용한다.
  수정 전 코드에서 실제 버그 때문에 실패하는지 실행하여 기대값·실제값·실패 이유를 기록한다.
  설치·포트·인증 fixture 오류나 컴파일 실패는 버그를 잡았다는 증거가 아니다.
- 구현 수정 후 같은 테스트와 같은 기대값으로 PASS를 확인하고 관련 기존 테스트도 실행한다.
  변경과 위험에 따라 실제 화면·DB·외부 효과의 결과를 확인한다.
  운영에서 발견한 버그도 같은 방식으로 회귀 보호를 남긴다.
- 실패한 기대값을 구현에 맞춰 바꾸지 않는다.
  요구사항 변경 또는 테스트가 기존 계약을 잘못 표현했다는 독립적인 근거를 적은 경우에만 기대값을 수정한다.
  실행 환경·fixture 수리는 행동 단언을 보존하고 기존에 무엇이 검증을 막았는지 설명한다.
- 새 보호나 크게 바뀐 보호는 현실적 mutation으로 탐지력을 확인한다.
  경계값 이동·권한 조건 제거 등 잡을 버그와 실패할 테스트를 먼저 예측하고, 별도 임시 복사본에서 결함을 주입해 실제 실패 이유를 확인한 뒤 원복한다.
  무관한 테스트나 cleanup에서만 실패했다면 예측한 보호의 증거로 포장하지 말고 테스트를 보완한다.
  이미 보호가 검증된 단순 문서 변경에 새로운 mutation을 의무화하지 않는다.

## 반복 실행 환경

- 공통 명령은 `./scripts/verify.sh`이며 로컬·verifier·CI가 동일하게 사용한다.
  실제 Node 24에서 Python hook fixture, lint, typecheck, build, TypeScript 테스트를 실행한다.
  매 편집마다 전체 테스트를 돌리지 않고 관련 검사 후 완료 전에 공통 검증을 수행한다.
- HTTP 통합 테스트는 프로덕션 Next 서버를 임의 포트에 띄우고 실제 세션과 임시 SQLite 파일 DB를 사용한다.
  시작 데이터를 명시하여 같은 상태에서 반복할 수 있어야 한다.
- 브라우저 검증은 해당 task 전용 데이터와 포트를 사용한다.
  초기화는 직접 만든 테스트 데이터에만 하며 사용자 data 폴더·기존 서버는 보존한다.
  외부 서비스가 있으면 테스트 키·sandbox를 쓰고 필요한 파일·네트워크 접근만 허용한다.
  로컬 SQLite만으로 독립 실행되므로 이 starter에 Docker는 필수가 아니다.

## 독립 리뷰와 완료

- verifier는 같은 PRD·가이드·변경 경로에 적용되는 Rules·현재 코드·테스트·diff를 직접 읽고 실행한다.
  테스트 PASS뿐 아니라 정답의 출처, 누락된 조건, 테스트 비용과 안정적인 경계도 리뷰한다.
- PRD의 검증 범위 표는 tests/api/ui의 required 또는 not-applicable과 이유를 선언한다.
  tests는 항상 required이며 API/UI는 실제 영향에 맞춘다.
  verifier는 diff로 비적용 근거를 확인한다.
  required 항목이 실행 불가면 BLOCKED이며 not-applicable로 바꿔 통과시키지 않는다.
- 결과는 AC-ID와 G-ID별 PASS/FAIL/BLOCKED, checks는 required의 PASS/FAIL/BLOCKED 또는 사전 비적용 항목의 N/A와 구체적 증거를 포함한다.
  JSON 존재나 테스트 통과가 실제 브라우저 확인을 대신하지 않는다.
- Hook은 임시 프로젝트 fixture에서 missing/fail/stale/pass/bounded-stop/기형 입력/역할 분리/초안 거절/검증 범위/완료 상태 전환을 확인한다.
- 로그·계획·인터뷰·검증·화면은 `.artifacts/<slug>/`에 보관하고 커밋하지 않는다.
  제공된 과거 로그와 verifier가 직접 실행한 결과를 구분한다.
- CI workflow가 있다는 사실과 원격 필수 검사·병합 보호가 설정됐다는 사실을 구분한다.
  PR 게시 시 실제 CI 상태를 확인하며 보호 설정을 확인하지 못했다면 병합이 강제로 차단된다고 주장하지 않는다.

편집·세션 훅 변경은 [훅 운영](hooks.md)의 fixture로 실제 입력/출력과 파일·작업 상태 보존을 확인한다.
편집 직후 ESLint 알림은 한 파일 검사이며 공통 검증이나 독립 리뷰의 PASS가 아니다.
